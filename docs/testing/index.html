Smoke Tests

Smoke tests run after CI/CD deployment to verify the deployed environment works. A smoke case is a scenario in tests/e2e/features/smoke/, tagged @smoke on its feature: worker-health, api-health, cron-jobs, pages and auth (see BDD (playwright-bdd)). The chromium-smoke project runs the @smoke scenarios of tests/e2e/features/.

Run locally:

npm run test:e2e:smoke   # bddgen, then the chromium-smoke project with the Cucumber reports

CI/CD: Runs after deployment using GitHub Environment credentials (dev or prod), with SHOULD_NOT_MUTATE (the factories read the deployment's data) and EXPECTED_VERSION (the version each worker reports). The step summary carries make bdd-report suite=smoke and make bdd-steps summary=1; the artifact bdd-smoke holds the Cucumber report.

NON-NEGOTIABLE RULES

Rule 0: One Level per Behaviour, the Lowest That Proves It

LevelProves
Unita pure function: parsing, a calculation, a schema, a token getter
Componentone component with its real children and stores: what it renders for its props and store state, which token it binds, what it emits
E2Einteraction and integration: a user's flow across pages, the URL, the server and the database (a booking lands as an order, a landing syncs its parameters, a claim moves a ticket)

A behaviour a unit or component spec proves gets no e2e case. A glyph, a colour, an alignment or a label is a component spec plus the browser check; the e2e case asserts the flow around it, in GIVEN/WHEN/THEN, as what the system does for the user.

An outcome is asserted in one case; a case that reaches an outcome another case asserts extends that case.

Rule 1: Tests MUST Be DRY

STOP before writing ANY test code and ask:

  • Am I copying code from another test? → EXTRACT to helper/factory
  • Am I writing similar test cases? → USE describe.each() / it.each()
  • Am I constructing test data manually? → USE FACTORY
// ❌ REJECTED: Manual data construction
const inhabitant = { id: 1, name: 'Anna', lastName: 'Hansen' }

// ✅ REQUIRED: Factory usage
const inhabitant = { ...HouseholdFactory.defaultInhabitantData('test-salt'), id: 1 }

// ❌ REJECTED: Repeated test cases
it('validates ADULT ticket', () => { ... })
it('validates CHILD ticket', () => { ... })
it('validates BABY ticket', () => { ... })

// ✅ REQUIRED: Parametrized tests
describe.each(['ADULT', 'CHILD', 'BABY'])('validates %s ticket', (ticketType) => { ... })

Rule 2: E2E Tests MUST Use Factories

Location: /tests/e2e/testDataFactories/

// ❌ REJECTED: Direct API calls or manual data
const response = await context.request.put('/api/admin/season', { data: { ... } })

// ✅ REQUIRED: Factory methods
const season = await SeasonFactory.createSeason(context, SeasonFactory.defaultSeason(testSalt))

Factory methods:

  • EntityFactory.defaultEntity(testSalt) - Create unique test data
  • EntityFactory.createEntity(context, data) - HTTP create with assertion
  • EntityFactory.deleteEntity(context, id) - Cleanup
  • EntityFactory.getEntity(context, id) - Fetch for verification

Factories on disk: AllergyFactory, BillingFactory, DinnerEventFactory, ExpenseFactory, FeedbackFactory, HouseholdFactory, NotificationFactory, OrderFactory, SeasonFactory, SeasonImportFactory, SenderFactory, SettingFactory, TicketFactory, UserFactory, WaitlistFactory; reconciliationTestData.ts holds the data for the four reconciliation outcomes of households, inhabitants and users, shared by unit and e2e specs.

Config values: a factory reads the app's config from the plain modules in app/config/, which app.config.ts imports: TicketFactory prices at DEFAULT_TICKET_PRICES (ticketPrices.ts), NotificationFactory reads notificationTemplates.ts. Playwright runs without Nuxt, so app.config.ts itself stays out of the specs.

Scenario methods:

  • SeasonFactory.createActiveSeason(context) - the singleton active season TestSeason-E2E-Singleton: the setup-season project (tests/e2e/season.setup.ts) creates and activates it once per run, before the spec workers start; a spec's call returns it, and global teardown deletes it after the run. A spec resolves it in beforeAll and a feature in the BeforeAll of fixtures.ts, so a run without setup-season (--no-deps) creates it there, outside a test's timeout. Its dinners are open (ticketIsCancellableDaysBefore 0); a case on a closed dinner creates its own season
  • SeasonFactory.createActiveSeasonFromTomorrow(context, testSalt, {days, deadline?, cookingDays?, startInDays?}) - a serial spec's own active season, returned as {season, dinnerEvents}: starts startInDays days from today at midnight (1 by default) and ends days days after the start, inside the pre-booking window (ADR-015); cookingDays picks 'all' or 'weekdays' over the default Mon/Wed/Fri; deadline is the cancel deadline in days. Serial only: activating it displaces the singleton active season
  • SeasonFactory.createCookingTeamWithChefAndDinner(context, season, chefInhabitantId, {teamName?, dinner?, day?}) - a cooking team of the season with the chef as CHEF and a dinner of the team with that chef, returned as {team, dinner}: dinner sets the dinner's fields (chefId: null leaves the duty vacant); day places the dinner on a free day of the season ('free', a browser spec) or alone on a given day (a serial spec), else on the date dinner names, tomorrow by default
  • DinnerEventFactory.createDinnerEventOnFreeDay(context, season, data?) - a browser spec's dinner alone on a free day of the season, picked at random after the season's last dinner where one is free; a day that turns double in the meantime gives the dinner up and another day is tried
  • DinnerEventFactory.createDinnerEventAloneOnDay(context, season, day, data?) - a serial spec's dinner alone on day: the dinners the season holds on that day give way. Serial only: a parallel spec's dinner on the day goes with them

Rule 3: E2E Tests MUST Be Parallel-Safe

// ❌ REJECTED: Hardcoded identifiers
const season = { shortName: 'Season-2025' }  // Will conflict in parallel

// ✅ REQUIRED: Salted unique data
const testSalt = temporaryAndRandom()
const season = SeasonFactory.defaultSeason(testSalt)  // TestSeason-<uuid>

Salt: temporaryAndRandom() (tests/e2e/testHelpers.ts, a UUID) gives a spec its salt; salt(base, testSalt) writes <base>-<testSalt>.

Names: the rows a spec or a factory creates match the LIKE patterns of the Makefile's d1-nuke-* targets, which make d1-nuke-all deletes. A person in a shared session household (the admin's or the member's, from getSessionUserInfo) is named salt('Anders', testSalt), and the role the spec reads goes into lastName; a person in a spec's own household goes with the household.

EntityPatternFactory default
SeasonshortName LIKE '%Test%'SeasonFactory.defaultSeason, SeasonFactory.E2E_SINGLETON_NAME
Householdname LIKE 'Test%' OR address LIKE 'Andeby%'HouseholdFactory.defaultHouseholdData
Inhabitantname LIKE 'Anders-%-%-%-%-%'HouseholdFactory.defaultInhabitantName (defaultInhabitantData, createInhabitantForHousehold)
Useremail LIKE '%@andeby.dk'UserFactory.defaultUser
AllergyTypename LIKE 'Peanuts-%' OR name LIKE 'Test %' OR name LIKE 'Updated %'AllergyFactory.defaultAllergyTypeData

testDataNaming.unit.spec.ts (Architecture Tests) checks the factory defaults against the patterns.

Households and users: a preference write re-scaffolds its household, so a case that writes preferences creates its own household (HouseholdFactory.createHousehold), which the admin writes with ?adminBypass=true; under the override the preference write keeps the season's deadlines. The session households hold the access cases. The admin and the member are the two users who log in: a role change runs inside UserFactory.withSystemRoles, which restores the roles, and the roles an endpoint accepts are proven in the requireHouseholdAccess unit table. The cases of a parallel suite that save the member's settings run in order in one worker: test.describe.configure({mode: 'serial'}) in a spec, @mode:serial on a feature.

ALWAYS verify: npx playwright test path/to/test.e2e.spec.ts --workers=4

One dinner per day in browser specs: the dinner and chef pages select a dinner by date, and a new team receives the season's generated dinners. A browser spec creates its dinner with DinnerEventFactory.createDinnerEventOnFreeDay(context, season, data), which puts it alone on a free day of the season, opens the page with ?date= on that day, and deletes the dinner in afterAll.

Rule 3a: E2E Interactions Wait for Hydration

The server renders a page's controls before Vue attaches their handlers, so a click or fill that lands first is lost. A test that interacts with a page waits for hydration after every navigation, through gotoHydrated; page.goto alone is for tests that only read.

// ❌ REJECTED: the fill lands on a dead control
await page.goto('/admin/teams?mode=create')
await page.locator('input#team-count').fill('2')

// ✅ REQUIRED: navigate, then wait for hydration
await testHelpers.gotoHydrated(page, '/admin/teams?mode=create')
await page.locator('input#team-count').fill('2')

Rule 4: Extract Repeated Patterns

Locations: /tests/e2e/testHelpers.ts (Playwright) and /tests/component/testHelpers.ts (Vitest)

If you write the same pattern twice → EXTRACT IT

// ❌ REJECTED: Repeated dropdown selection
await page.getByTestId('season-selector').click()
await page.getByRole('option', { name: seasonName }).first().click()

// ✅ REQUIRED: Use helper
await testHelpers.selectDropdownOption(page, 'season-selector', seasonName)

An extracted helper replaces every copy. The change that extracts it greps every spec for the pattern its body wraps and moves each hit onto the helper in the same change; a local copy left beside the helper is a broken window.

Rule 5: No console.log in Tests

// ❌ REJECTED
console.log('result:', result)

// ✅ REQUIRED
expect(result).toBe(expectedValue)

Rule 6: Component Tests Test REAL Code

Guiding principle: a component test exercises the real component tree, the real composables and the real stores. The only thing faked is what the test environment cannot provide - and in practice that is HTTP.

A mock proves nothing about the code it replaces. When a spec renders a hand-written UserListItem stand-in, it keeps passing after the real UserListItem renames its #badge slot - while the page breaks. Every mocked house component is a second copy of a contract, maintained by hand, that the suite has silently stopped checking.

LayerIn component testsHow
Component under test and its childrenREALRender them. Supply the context they need: mountWithTooltipProvider() for anything containing UTooltip
Composables, validation schemas, utilsREALNothing to do
Pinia storesREALresetStores() in beforeEach: fresh stores over a fresh data layer per test; the store fetches from the registered endpoints
HTTPFAKEregisterEndpoint() per route - specific FIRST, generic LAST
Nuxt runtime the test drives (useRoute, navigateTo, useUserSession)FAKE when the test steers itmockNuxtImport() over tests/component/hoistedMocks.ts (mockRouteAndNavigation, mockSession)
Browser-only or third-party APIs the environment lacksFAKE, with a reasonmockNuxtImport() + a comment naming the gap
// ❌ REJECTED: mocking a house component to dodge a provider
mockComponent('UserListItem', {setup: () => () => h('div')})

// ❌ REJECTED: mocking a store to dodge its fetch
mockNuxtImport('useUsersStore', () => () => ({allergyManagers: ref([])}))

// ✅ REQUIRED: real component, real store, faked HTTP
registerEndpoint('/api/admin/users/by-role/ALLERGYMANAGER', () => [])
const wrapper = await mountWithTooltipProvider(AdminAllergies, {props: {canEdit: true}, isMd: false})

Every remaining mock needs a comment naming what the environment cannot provide. "To avoid tooltip issues" is not a reason - it is a missing helper. Specs that still mock stores or house components are debt: migrate them when you touch them.

BDD (playwright-bdd)

bddgen (npm run test:bdd:generate) generates a Playwright spec per feature into .output/bdd/<suite>/; the Playwright projects, the setup projects and the factories run the scenarios. A project picks its scenarios by tag through defineBddProject in playwright.config.ts (chromium-smoke: @smoke). A feature carries one suite tag: @smoke, @api-parallel, @api-serial, @e2e-parallel or @e2e-serial; a parallel feature whose scenarios save the member's settings also carries @mode:serial (Rule 3). A *.e2e.spec.ts migrates to features when a change touches it; its cases become the scenarios and example rows that check the same behaviours. Rules 0 to 5 hold for the steps.

PathHolds
tests/e2e/features/<domain>/*.featureThe scenarios, tagged with their suite on the feature
tests/e2e/steps/<domain>.steps.tsThe steps of a domain and its parameter types: auth, billing, booking, health, household, maintenance, notification, pages, season, user
tests/e2e/fixtures.tsplaywright-bdd's test merged with the UI specs' test (tests/e2e/uiTest.ts), the fixtures, the scene helpers, Given/When/Then/BeforeAll (createBdd)
.output/bdd/<suite>/The generated specs, gitignored

Fixtures. test carries the UI specs' API error guard: a scenario fails at its end on a 4xx or 5xx from /api/ that testHelpers.expectApiError declares nowhere. adminContext is the admin's stored session (validatedBrowserContext), closed after the scenario. contextOf(actor) opens an actor's context on first use: the user's stored session (memberValidatedBrowserContext), or a visitor's context without a session (openContext). A GIVEN that signs in puts its context in scene.context, and contextOfActor(scene, actor) reads it, so one step serves each actor. scene holds what the steps of one scenario hand each other; fromScene(scene, key) reads what an earlier step set.

The scene helpers create a scenario's data through the factories and record it for the cleanup: createSceneHousehold, createScenePerson and createDinnerInThePastMonth. activeSeasonOf reads the season a GIVEN activated, else the singleton, which the BeforeAll resolves per feature. personOf reads an actor's inhabitant, adultPriceIdOf the season's ADULT price, and periodOf the billing period that bills the scenario's households. After the scenario, the scene puts back the member's settings and deletes the rows it created. Each cleanup step runs, and the failed steps fail the scenario together (AggregateError).

  Background:
    Given the admin is signed in

  Scenario Outline: The <job> job runs successfully
    When the <job> job runs

    Examples:
      | job               |

Scenarios are DRY. A feature states each behaviour once, and Gherkin carries the variation (tests/e2e/features/notifications/booking-notifications.feature is the model).

  • A Scenario Outline carries the values a behaviour is checked with: one row per case, one column per kind of value (| palette | text scale |, | channel | emails sent |). Each group of related values has its own Outline: the channels in one, the appearance in another.
  • A cell holds the bare value (seller, colorblind, 1). The words every row shares live in the template: sent to the closest user of the <inhabitant>.
  • A situation is composed from small numeric steps: <waiting> inhabitants are on the waiting list and <for sale> tickets are for sale build every waiting-list state of the booking notifications.
  • An outcome is a count in an integer column, read by {int} with (s) and is/are: <emails sent> <notification> emails are sent to … reads 0, 1 and 2.
  • A Background carries the GIVENs every scenario of the feature shares; a Rule: with its own Background groups the scenarios that share more.
  • An Outline's name carries its columns, so each row names its scenario.
  • A THEN reads what is observable: the delivery records in the database, the CSV archives uploaded, the emails sent, what the user sees on the page.
  • The words are the domain's, as the code names them: the models and enums of prisma/schema.prisma and the validation composables, the words users read in app/config/ (bookingWords.ts), the actors below. A noun, a value or an event in a feature is one those sources hold, looked up before it is written: a ticket has a ticket type (ADULT, CHILD, BABY) and a guest ticket is booked on an inhabitant; a dinner mode is DINEIN, DINEINLATE, TAKEAWAY or NONE; the accountant link opens a billing period. A WHEN names the event (the dinner is booked, the ticket is released).

Step definitions are reused. One definition states one fact for every actor, value and suite.

  • A step names a domain fact: Then the active season has dinner events, When the DAILY_MAINTENANCE job runs. The page, the request and the locator live in the step body.
  • One phrasing per fact. npx bddgen export lists the steps; read it before writing a step, and reuse the one that states the fact. npx bddgen export --unused-steps lists the steps no scenario uses.
  • The actor is a parameter type bound to the domain: the user (User), the admin (SystemRoleSchema.enum.ADMIN), the chef, an inhabitant and its roles on a dinner (the seller, the first in line), the user's inhabitant (Inhabitant.userId), a visitor without a session. {actor} saves the setting {setting} serves each, and the step reads the actor's context from scene.
  • A domain word is a parameter type (defineParameterType) built from its enum schema. A cell and a step text hold the enum value as it is: {job} reads DAILY_MAINTENANCE, {notification} reads WAITLIST_JOINED, {mode} reads DINEIN; {setting} reads the name and the value together (palette colorblind, channel EMAIL). The type's regexp lists the enum values, so a value outside the enum fails at generation.
  • One text serves GIVEN and THEN: the GIVEN sets the fact, the THEN reads it (the user has the setting channel EMAIL). The BDD projects set matchKeywords: true, so the keyword picks the body.
  • A UI body of a step carries the UI suites' tag ({tags: '@e2e-parallel or @e2e-serial'}) and serves the UI features; the untagged body serves the api features.
  • An optional parameter is a second pattern on the same body: the dinner is booked and the dinner is booked for {actor}.
  • Steps live in the file of their domain.
  • Scenario state and its cleanup live in fixtures (scene); data comes from the factories, salted (Rules 2 and 3).
  • GIVEN sets the scene, WHEN acts, THEN reads the outcome. A THEN that reads standing state needs no WHEN (Then the users list is non-empty).
  • A block of Gherkin comes for review with its reuse table: each step text, its definition, and the lines that use it.

Commands.

npm run test:bdd:generate                     # generate .output/bdd/ from the features
npx bddgen export                    # the step definitions
npm run test:e2e:smoke               # generate, then run the smoke suite with its reports
npm run test:bdd:generate && npx playwright test --project=chromium-smoke --grep "<scenario>" --reporter=line   # one scenario by its title

Reports. A BDD suite's npm script sets BDD_SUITE=<suite> and passes no --reporter, so the reporter list of playwright.config.ts writes the Playwright html, line and json reports and the Cucumber reports .output/bdd/reports/e2e-<suite>-bdd.json and .output/bdd/reports/e2e-<suite>-bdd/index.html (outside test-results/, which Playwright empties when a run starts). The Cucumber html drops traces (application/zip); the smoke html keeps no attachment. CI uploads the two as the artifact bdd-<suite>; make bdd-report suite=<suite> writes the summary table and make developer-assemble publishes the Cucumber html as the suite's report. make bdd-steps (summary=1 for the one line) counts every step line of every feature against the definition bddgen matches it with (scripts/bdd-steps.mjs, no run needed): lines, definitions, uses per definition, the definitions used once or unused and the lines without a definition. A new step phrasing is a definition used once; reuse an existing phrasing before adding one.

Test Helper Utilities

Location: /tests/e2e/testHelpers.ts

import testHelpers from '../testHelpers'
const { validatedBrowserContext, pollUntil, selectDropdownOption } = testHelpers

validatedBrowserContext(browser)

Authenticated browser context for API requests.

const context = await validatedBrowserContext(browser)
const season = await SeasonFactory.createSeason(context)

UI cases and API errors: openContext(browser, options?), expectApiError(context, status, url)

A UI spec imports test from tests/e2e/uiTest.ts. Its auto fixture records the /api/ responses of the case's pages: the built-in context and every context from openContext, through which validatedBrowserContext, memberValidatedBrowserContext and freshMemberContext open theirs. A 4xx or 5xx the case did not declare fails the case at its end, naming the method, the url and the status. A case that drives an error on purpose declares it before the action; requests through context.request (the factories) are not recorded.

expectApiError(context, 401, '/api/')

pollUntil(fetchFn, condition, maxAttempts?, initialDelay?)

Polling with exponential backoff. Preferred over page.waitForTimeout().

const teams = await pollUntil(
  () => SeasonFactory.getCookingTeamsForSeason(context, seasonId),
  (teams) => teams.length === 3
)

selectDropdownOption(page, dropdownTestId, optionName)

Handles Linux strict mode violations with dropdowns.

await selectDropdownOption(page, 'season-selector', 'TestSeason-123')

doScreenshot(page, name, isDocumentation?)

Debug or documentation screenshots.

await doScreenshot(page, 'dropdown-timeout')  // Debug: test-results/
await doScreenshot(page, 'admin/page', true)  // Docs: docs/screenshots/

    (await import('~~/tests/component/hoistedMocks')).mockRouteAndNavigation({path: '/admin/economy'}))

Component Testing (Nuxt UI v4+)

Nuxt test environment (@nuxt/test-utils 4)

The Nuxt app starts in a per-file beforeAll. Rules for *.nuxt.spec.ts:

  • A composable whose chain reaches useAppConfig()/useNuxtApp() (useSeason, useBooking, useBookingUi, useBilling, useMaintenance) runs in beforeAll or in the test — at module level or in a describe body it throws NUXT_E1001. Declare let bindings and destructure in one beforeAll per file; call sites stay unchanged.
  • Collection-time data (it.each tables, module constants) reads the config via import appConfig from '~/app.config'.
  • Override a module per export: spread importOriginal() and replace the one export the spec steers (vue-router's useRoute), or mockNuxtImport for an auto-import (useToast, navigateTo). The runtime boots the real router and the real config; a wholesale vue-router, #imports or useRuntimeConfig mock breaks the boot.
  • The nuxt vitest project (vitest.config.ts) sets hookTimeout: 60_000 (a cold app boot under full parallel load passes the 10s default) and runtimeConfig.public.HEY_NABO_API for specs that render Heynabo links.

Testing UForm Submission

The Problem: In happy-dom, trigger('click') on a <button type="submit"> inside a <form> does NOT reliably fire the form's @submit handler. Validation-gated emits appear to silently drop.

The Solution — NuxtUI useTemplateRef pattern:

Component wires the button outside the implicit form-submit flow and calls the form's submit() method via ref. This is the NuxtUI-documented pattern for buttons outside <form> scope (modal footers, UCard #footer, etc.) — and it happens to be test-friendly.

<script setup lang="ts">
import type {Form, FormSubmitEvent} from '@nuxt/ui'

const formRef = useTemplateRef<Form<MyFormData>>('formRef')

const handleSubmit = (event: FormSubmitEvent<MyFormData>) => {
    emit('save', event.data)
}
</script>

<template>
    <UForm ref="formRef" :state="formState" :schema="MyFormSchema" @submit="handleSubmit">
        <!-- fields -->
        <template #footer>
            <UButton
                v-bind="BUTTONS.save"
                data-testid="my-form-submit"
                @click="formRef?.submit()"
            >
                Gem
            </UButton>
        </template>
    </UForm>
</template>

Test pattern — click the button, flush promises:

import {flushPromises} from '@vue/test-utils'

const clickSubmit = async (wrapper: Awaited<ReturnType<typeof mount>>) => {
    const submitBtn = wrapper.findAll('button').find(b => b.text().includes('Gem'))
    await submitBtn!.trigger('click')
    // UForm.submit() validates schema + contextual rules asynchronously
    await flushPromises()
    await nextTick()
}

it('emits save with valid data', async () => {
    const wrapper = await mount()
    // ...fill fields...
    await clickSubmit(wrapper)
    expect(wrapper.emitted('save')).toBeTruthy()
})

it('does not emit save when validation fails', async () => {
    const wrapper = await mount()
    // ...fill only some fields or violate contextual rules...
    await clickSubmit(wrapper)
    expect(wrapper.emitted('save')).toBeFalsy()
})

Key rules:

  1. Always use ref="formRef" on UForm + @click="formRef?.submit()" on the submit button. Do NOT rely on type="submit" — it works in production but is flaky in tests.
  2. Always await flushPromises() then await nextTick() after click. Schema + :validate function both run async; the emit happens after they resolve.
  3. Never hardcode formatted values. Use the same utility the component uses (e.g. formatDate() from ~/utils/date) so the assertion stays correct if the format changes.
  4. Dates in form state should be strict z.date() in form schemas — not z.coerce.date(). Coercion silently accepts null as 1970-01-01 and fails your "missing date blocks submit" tests.

Architecture Tests

tests/component/architecture/*.unit.spec.ts read sources — the .vue files under app/, the SQL under migrations/, the palettes under app/assets/css/palettes/, the Makefile — and fail on a pattern, not on a render. They are how a design-system sweep stays swept: once every <UAlert> binds an ALERTS kind, the test is what stops the 57th one from being written with a raw :color (ADR-018). Violations are reported as file:line, so a failure names the sites to fix.

Add one whenever a fix to a Nuxt UI component family becomes a token: add the token, sweep all instances, add the rule.

A property check runs one case per dimension — a rule, a palette and mode — that collects every failing item and prints them in its message (expect(misses).toEqual([])). One case per item turns a 50-case suite into thousands and says the same thing.

designSystemContrast.unit.spec.ts — the palette's contrast, not its class strings

The one architecture test that reads values instead of sources, and it is still a property, not a token value: it encodes EN 301 549 → WCAG 2.1 contrast. It resolves every colour the design system names through the same stylesheets the browser reads (main.css @theme static, Tailwind 4's oklch defaults, app.config.ts ui.colors, Nuxt UI's --ui-* semantics), composites the alpha surfaces (bg-primary/10, bg-gray-800/50), and measures (L1 + 0.05) / (L2 + 0.05) for every pair the tokens define — light and dark. Thresholds: 4.5:1 body text (1.4.3 AA), 3:1 borders, rings and outlines (1.4.11 AA), 7:1 for the Høj kontrast palette preset (1.4.6 AAA). The colour maths lives in tests/component/architecture/contrast.ts (hexToRgb, oklchToHex, relativeLuminance, contrastRatio, composite) so the palette generator reuses the same functions it is measured by — no colour dependency, no second implementation.

The pairs are derived by walking the exported tokens, so a token added tomorrow is measured tomorrow. Four groups: text on the neutral surfaces (BG.panel, BG.inset, …), a token that carries both its ink and its fill (hero backgrounds, calendar days, kitchen panels, Pantone chips), borders/rings against the page and BG.panel (an edge that carries meaning on a token with its own fill, MEANINGFUL_EDGES_ON_FILL such as the ticket faces, also against that fill), and the Nuxt UI semantic slots (text-<slot> on the page and on the soft bg-<slot>/10 alert surface, text-inverted on the solid fill). Three scoping rules keep the inventory on the standard: a token whose own classes make its text large-scale (24px, or 18.66px bold) is measured at the 3:1 rung of 1.4.3; a fill takes its bar from the typography a component places on it (INK_ON_FILL, one row per surface with the component and line that draws it); and the dividers and table banding listed in docs/ui.md "Palettes" sit outside 1.4.11.

Every palette under app/assets/css/palettes/ — the base default.css and each preset — is measured at the level its PALETTES entry carries (tests/component/architecture/palettes.ts derives the list from the registry). color="neutral" badges, buttons and alerts are measured on the faces Nuxt UI gives them (bg-inverted, bg-elevated, bg-elevated/50). One case per palette and mode lists every pair below its bar and expects exactly the pairs listed in PRESET_FINDINGS. The palette files are generated and committed, and the specs measure them as committed: after a change to the main.css scales, ui.colors or a token that adds a fill or an ink, make palettes regenerates them before the specs run.

designSystemColourVision.unit.spec.ts measures the meaning pairs of designSystemMeanings.ts (shared with the generator) under protanopia, deuteranopia and tritanopia for the base and every colourSafe palette, and the rainbow stops apart in every palette; its case per palette and mode expects exactly the pairs listed in FINDINGS (the base's meaning pairs).

When it fails, fix the token — never the threshold. A listed pair cuts both ways: a green pair that starts failing and a listed pair that starts passing both fail the case, and the second asks for the entry to be deleted. Never add an entry to silence a new failure — a new miss is a regression.

Do NOT assert design-token values. expect(ui.title).toContain('text-lg') restates the design and guards nothing — the colour, size and padding of a token are the user's visual check. Architecture tests assert usage; component specs assert behaviour (text renders, CTA present or absent, events emitted); e2e asserts no horizontal overflow at 375px (MobileViewport.e2e.spec.ts). A getter that branches on isMd may get one case per branch.

Testing Time-Sensitive Behavior (Deadlines)

The Problem

Business logic often depends on deadlines (e.g., "can only cancel 2 days before dinner"). Tests must:

  1. Use the same deadline logic as the application
  2. Create predictable test data that guarantees specific deadline scenarios
  3. Not rely on UI defaults (which may use singleton season with different config)

Strategy: Control the Season, Control the Deadline

Serial tests create their own season with the deadline their cases need: SeasonFactory.createActiveSeasonFromTomorrow creates it with its dinners from tomorrow and activates it. The season in tests/e2e/ui/serial/HouseholdScaffolding.e2e.spec.ts (beforeAll) cooks every day with a 2-day deadline, so it holds dinners after and before the deadline.

Result with 2-day deadline:

  • Events 3+ days away → BEFORE deadline (can CREATE, DELETE)
  • Events 1-2 days away → AFTER deadline (can only RELEASE, CLAIM)

Minimal seasons: a season spans the dinners the case proves, one when one is enough, inside the pre-booking window (ADR-015 § Test Requirements) unless the case proves a dinner past it (PAST_THE_SCAFFOLD_WINDOW_DAYS).

Use Application's Deadline Logic

CRITICAL: Tests MUST use the same deadline calculation as the application.

// ❌ WRONG: Custom calculation that differs from application
const daysAway = Math.ceil((de.date.getTime() - now.getTime()) / (1000 * 60 * 60 * 24))
const isAfterDeadline = daysAway <= deadline

// ✅ CORRECT: Use application's pure utility functions
import {isBeforeDeadline, getDinnerTimeRange} from '~/utils/season'

// Hardcoded from app.config.ts (Nuxt auto-imports not available in Playwright)
const DEFAULT_DINNER_START_HOUR = 18

const canModifyOrders = (dinnerEventDate: Date): boolean => {
    const dinnerStartTime = getDinnerTimeRange(dinnerEventDate, DEFAULT_DINNER_START_HOUR, 0).start
    return isBeforeDeadline(testSeason.season.ticketIsCancellableDaysBefore, 0)(dinnerStartTime)
}

const beforeDeadlineEvents = dinnerEvents.filter(de => canModifyOrders(de.date))
const afterDeadlineEvents = dinnerEvents.filter(de => !canModifyOrders(de.date))

Setup via API with Explicit Parameters

Problem: UI endpoints may use fetchActiveSeasonId() internally, which could return a different season than expected.

Solution: Use factory methods with explicit seasonId parameter:

// ❌ WRONG: Relies on UI which uses active season (might not be test season)
await page.getByTestId('inhabitant-123-preferences-edit-mandag-DINEIN').click()
await page.getByTestId('save-preferences').click()

// ✅ CORRECT: API with explicit seasonId ensures correct deadline calculation
await HouseholdFactory.updateInhabitantPreferences(
    adminContext,

    preferences,

)

Testing Scaffolder Buckets (ADR-016)

The scaffolder has four action buckets based on deadline:

BucketWhenAction
CREATEBefore deadline, no existing orderCreate new BOOKED order
DELETEBefore deadline, existing order, prefs=NONEDelete order
RELEASEAfter deadline, existing order, prefs=NONEUpdate to RELEASED (not delete!)
CLAIMAfter deadline, released ticket availableClaim from marketplace

Test pattern for RELEASE bucket:

test('RELEASE bucket: after-deadline orders are RELEASED not deleted', async ({browser}) => {
    const adminContext = await validatedBrowserContext(browser)
    const {userId: adminUserId} = await getSessionUserInfo(adminContext)

    // GIVEN: Inhabitant with DINEIN preferences
    const dineInPrefs = createDinnerModeWeekdayMap(DinnerMode.DINEIN)
    const inhabitant = await HouseholdFactory.createInhabitantWithConfig(adminContext, householdId, {
        name: salt('Test', testSalt),
        dinnerPreferences: dineInPrefs
    })

    // GIVEN: Trigger scaffold to create orders for BEFORE-deadline events
    await HouseholdFactory.updateInhabitantPreferences(
        adminContext, inhabitant.id, dineInPrefs, 200, testSeason.season.id!
    )

    // GIVEN: Manually create orders for AFTER-deadline events
    // (Scaffold can't create these by design - deadline has passed)
    for (const afterDeadlineEvent of afterDeadlineEvents) {
        await OrderFactory.createOrder(adminContext, {
            householdId,
            dinnerEventId: afterDeadlineEvent.id,
            orders: [{
                inhabitantId: inhabitant.id,
                bookedByUserId: adminUserId,
                ticketPriceId: ticketPrice.id,
                dinnerMode: DinnerMode.DINEIN
            }]
        })
    }

    // WHEN: Change preferences to NONE
    const nonePrefs = createDinnerModeWeekdayMap(DinnerMode.NONE)
    await HouseholdFactory.updateInhabitantPreferences(
        adminContext, inhabitant.id, nonePrefs, 200, testSeason.season.id!
    )

    // THEN: After-deadline orders should be RELEASED (not deleted)
    const ordersAfter = await OrderFactory.getOrdersForDinnerEventsViaAdmin(adminContext, eventIds)
    const releasedOrders = ordersAfter.filter(o =>
        o.inhabitantId === inhabitant.id && o.state === OrderState.RELEASED
    )
    expect(releasedOrders.length).toBe(afterDeadlineEvents.length)

    // THEN: Before-deadline orders should be DELETED (not in results)
    const bookedOrders = ordersAfter.filter(o =>
        o.inhabitantId === inhabitant.id && o.state === OrderState.BOOKED
    )
    expect(bookedOrders.length).toBe(0)
})

Key insights:

  1. Serial because: Test activates its own season (only one active at a time)
  2. All-days cooking: Predictable event count regardless of what day tests run
  3. Short deadline (2 days): Guarantees after-deadline events exist
  4. Manual after-deadline orders: Scaffold can't create past-deadline orders, so test creates them directly
  5. API with explicit seasonId: Ensures scaffold uses test season's deadline config

Pre-Completion Checklist

Before completing ANY test task:

  • Real: Component tests render real components and stores; only HTTP is faked (registerEndpoint), every other mock carries a reason comment
  • DRY: No duplicate code between tests
  • Parametrized: Similar cases use describe.each() / it.each()
  • Factories: E2E data created via factories
  • Salted: E2E data uses testSalt for uniqueness
  • Helpers: Repeated patterns in testHelpers.ts
  • Parallel: E2E verified with --workers=4
  • Once: an outcome is asserted in one case, at the lowest level (Rule 0)
  • Own household: a case that writes preferences creates its own household (Rule 3)
  • No console.log: Only expect() assertions

If ANY fails → STOP and refactor.
